# FairMatch Bangalore — Build Plan

An agentic AI system that matches Bangalore engineering students to real internship opportunities, compares allocation policies for fairness, and explains every decision. SDG 8 (decent work), SDG 10 (reduced inequality), SDG 16 (transparent, accountable institutions).

**Read this whole file before starting any phase. Build only what the demo needs. Commit to git at the end of every phase.**

---

## 1. The problem (keep this in mind while building)

India has a large education-to-employment gap: youth unemployment is far higher than overall unemployment, and skill mismatch is a major cause. At the scale of a city like Bangalore, internship and project opportunities are allocated with incomplete information:
- students don't find opportunities that fit them (SDG 8),
- the same well-connected students keep getting selected while others get none (SDG 10),
- nobody can explain or contest why a decision was made (SDG 16).

FairMatch is a decision-support tool for anyone allocating opportunities to many people: college placement cells, internship schemes, hackathon/project organisers, skilling programmes. A human always approves the final decision.

## 2. Demo script (build exactly this)

1. **Ask:** user types *"Find the best 3 candidates for the ML internships in Koramangala and explain why."* → the **live agent trace** panel shows Planner → Matcher → Equity Analyst → Auditor → Explainer, with each tool call, as it happens. Result: ranked candidates with skill-match breakdown.
2. **Map:** Bangalore map with real opportunities pinned by area, coloured by domain; students' home areas as a heat layer.
3. **Policy Lab:** allocate all opportunities under 3 policies (`skill_first`, `equal_access`, `hybrid`) → side-by-side chart of avg skill fit, Gini coefficient, unique recipients, repeat-selection rate. One-line takeaway generated by the Equity agent.
4. **Decision log + appeal:** decision cards (selected, reasons, runner-up, policy). Approve button. Appeal button → student states a reason → Auditor re-evaluates and the outcome + explanation is logged.

## 3. Data

### 3a. Real data — opportunities
- Primary: Kaggle "Internshala Dataset" (`aayush9119/internshala-dataset`): internship title, company, location, duration, stipend. **The user downloads the CSV manually into `data/raw/`** (Kaggle requires login).
- Optional: Kaggle "12000 Data Science Jobs In India – Naukri.com" (`anandhuh/data-science-jobs-in-india`) — has a skills column, useful for building the skill vocabulary.
- Loader: filter to Bangalore/Bengaluru (all spellings), deduplicate, normalise into the opportunity schema. Derive `required_skills` from the title (+ skills column if present) with a deterministic keyword→skill map. Assign each listing a Bangalore area and lat/lon (use the location text if specific, else a seeded random area from a fixed list of ~15 tech areas with known coordinates). Keep ~40–80 opportunities.
- If the raw CSV is missing, fall back to a bundled synthetic Bangalore opportunity set so the app always runs.

### 3b. Synthetic data — students
- Seeded generator, ~150 students across Bangalore engineering colleges (generic names like "College A–H", no real people), varied branches, home areas, skills with levels 1–3, interests, goals, weekly availability, and `past_opportunities` count.
- **Deliberately skewed history:** ~15% of students hold most past opportunities, so the fairness problem is visible in the data.

### 3c. Real data — Google Form (optional, drop-in)
Same schema as synthetic students, imported from a CSV export. Form columns:
`Anonymous ID | Branch | Year | Home area in Bangalore | Python | Java | ML | Data analysis | Web dev | App dev | Cloud/DevOps | Design | Communication | Leadership (each Beginner/Intermediate/Advanced/None) | Interests (multi-select) | Goal (internship / research / hackathons / leadership) | Hours available per week | Internships/projects received so far (0,1,2,3+) | Consent checkbox`
Rows without consent are dropped. No names, phone numbers or emails.

### Schemas
- **Student:** `id, branch, year, home_area, lat, lon, skills{skill:0-3}, interests[], goal, hours_per_week, past_opportunities, source(synthetic|form)`
- **Opportunity:** `id, title, company, area, lat, lon, domain, required_skills[], preferred_skills[], duration_weeks, stipend, slots, source(kaggle|synthetic)`
- **DecisionRecord:** `id, timestamp, opportunity_id, selected[], runner_up, policy, score_breakdown{per skill}, reasons[], constraints, status(proposed|approved|appealed|revised), appeal{text, outcome, explanation}`

## 4. Deterministic tools (`tools/`, plain functions, unit-tested)
- `search_students(filters)`, `search_opportunities(filters)`
- `score_match(student, opportunity)` → score + per-skill breakdown
- `rank_candidates(opportunity_id, k)`
- `allocate(policy)` → assignments for all opportunities. `skill_first` = pure fit; `equal_access` = prioritise low `past_opportunities` among eligible; `hybrid` = fit × access adjustment.
- `fairness_metrics(assignments)` → avg fit, Gini of opportunities per student, unique recipients, repeat-selection rate
- `log_decision(record)`, `get_decision(id)`, `appeal_decision(id, reason)`

All decisions come from these tools. **The LLM never invents a score or a reason.**

## 5. Agents (`agents/`, simple tool-calling loop, no heavy framework)
- **Planner:** turns the user request into an ordered list of steps/tool calls.
- **Matcher:** runs scoring/ranking tools.
- **Equity Analyst:** checks concentration, compares policies, flags if the proposal increases inequality.
- **Auditor:** verifies the proposal against rules (eligibility, slots, availability); handles appeals.
- **Explainer:** writes the explanation **only from the DecisionRecord fields**.

**Trace:** every step emits an event `{agent, action, tool, args, result_summary, duration_ms}` to an event list that the UI renders live (streamed as it happens, not after).

**LLM:** provider-agnostic wrapper. Default Gemini (free tier, key in `.env`), fallback Ollama. **Also a no-LLM "demo-safe" mode** with a rule-based planner/explainer, so the demo never breaks if the API fails.

## 6. UI (Streamlit, 4 pages, clean and modern)
Ask (chat + live trace side panel) · Map (pydeck) · Policy Lab (Plotly charts) · Decision Log (cards with Approve / Appeal). Consistent colour per agent in the trace. A small header line: "SDG 8 · 10 · 16".

## 8. Phases (stop and commit after each)
- **Phase 1 — Data + tools.** Pipeline, schemas, all tools, tests. Checkpoint: `python -m tools.demo` prints top candidates for one opportunity and fairness metrics for all three policies.
- **Phase 2 — Agents + trace.** LLM wrapper, 5 agents, trace events, demo-safe mode. Checkpoint: `python -m agents.cli "Find the best 3 candidates for ML internships in Koramangala"` prints the trace and answer.
- **Phase 3 — UI + README.** 4 pages as in the demo script; README explaining the architecture, agent flow, data sources, and which feature maps to which SDG, written for a student learning agentic AI. Checkpoint: the full demo script runs.

## 9. Non-goals
No auth, no database (JSON/CSV files), no deployment, no team-formation feature unless everything else is done, no scraping websites.
